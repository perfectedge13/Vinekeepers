# Vinekeepers

Vinekeepers is an AI-based bots collection. The bot core provides bootstrap, configuration (YAML), engine, tool registry, and audit logging.

## Build and run

- **Compile:** `mvn compile`
- **Tests:** `mvn test` (unit tests cover core components: config, core, env, events, state, bot, workflow, connectors). JUnit runs test **classes** in parallel by default (`src/test/resources/junit-platform.properties` and matching Surefire `configurationParameters` in `pom.xml`); methods in a class stay on one thread.
- **Spec schema gate:** `npm run validate-specs`
- **Spec drift gate:** `npm run validate-drift`
- **Docs gate:** `npm run validate-docs`
- **Main class:** `com.vinekeepers.VinekeepersApp` — run from your IDE or after packaging (e.g. `mvn package` then run the JAR with dependencies on the classpath).

Requirements: Java 21, Maven, Node 18+ for the spec gates.

### Docker

Build uses a **Java 21 JDK (Alpine)** stage; the **runtime image is Ubuntu Jammy** with **`git`**, **`openssh-client`**, and **`ansible`** (apt) so **ensure_repo_workspace** can shallow-clone when **`VINEKEEPERS_ALLOW_GIT_CLONE=true`** and **`AnsiblePlaybookDeployRunner`** can run **`ansible/playbooks/site.yml`** without fragile pip-on-Alpine installs. The image sets **`VINEKEEPERS_REPO_WORKSPACE_ROOT=/app/checkouts`** by default; clones live there and are **ephemeral** unless you mount a volume (e.g. `-v vinekeepers-clones:/app/checkouts`).

```bash
docker build -t vinekeepers .
docker run --rm -e LUNA_DISCORD_TOKEN=your_token -e ARRIETTY_DISCORD_TOKEN=your_arrietty_token -e GADGET_DISCORD_TOKEN=your_gadget_token vinekeepers
```

Or use Compose (optionally add a `.env` file with `DISCORD_BOT_TOKEN=...`; `compose.yaml` already reads `.env`):

```bash
docker compose up -d
```

To override config or env from the host when using `docker run`, mount volumes:

```bash
docker run --rm -v "$(pwd)/config:/app/config" -v "$(pwd)/.env:/app/.env" vinekeepers
```

**Gadget / `run_deploy_compose` on Docker:** the DevOps Discord flow offers compose **up**, **stop**, **restart**, and **ps** (status) per target in `config/deploy-targets.yaml`. The `compose ps` path now posts into **`DevOps Progress`**; mutating compose operations still use **`deploy-progress`**. Direct host compose operations run `docker compose` on the **host** engine from inside the Vinekeepers container, so the runtime image must include the Docker CLI + Compose plugin and the container must mount **`/var/run/docker.sock`** plus each compose target's **`workingDirectory`** at the path visible inside the container.

`compose.yaml` is set up for **Gadget** when you run with Compose: it mounts **`/var/run/docker.sock`**, bind-mounts the repo to **`/workspace/vinekeepers`** (override with **`VINEKEEPERS_HOST_REPO_ROOT`**), bind-mounts the shipped stack paths **`/home/perfect_edge13/Docker/neo4j`** and **`/home/perfect_edge13/Docker/wikijs`** at the same absolute paths inside the container, and sets **`DEPLOY_TARGETS_PATH=/app/config/deploy-targets.docker.yaml`**. If those host paths differ on your machine, update **`config/deploy-targets.yaml`**, **`config/deploy-targets.docker.yaml`**, and the **`volumes`** entries in **`compose.yaml`** together.

If you run Vinekeepers outside Docker, keep using **`config/deploy-targets.yaml`** and unset container-specific paths. If the socket, compose file, or working directory is still missing inside the container, Gadget fails fast and Vinekeepers logs startup warnings before the first Discord-triggered compose request. Rebuild and restart the Vinekeepers container after image or runtime changes so the live bot picks up the Docker CLI and compose preflight behavior. Prefer **`hostOpsExecutor: direct`** when the container has the Docker CLI and matching mounts; otherwise use **`cursor_agent`**.

Optional: set `JAVA_OPTS` (e.g. `-Xmx512m`) via `-e JAVA_OPTS=...`.

Bot definitions and routing are in `config/bots.yaml`. Discord identity is **connector-scoped** under `identities.discord`: each bot may set `identities.discord.tokenEnvKey` to the env var name for that bot's token (never put raw tokens in config). **handlesOwnedSpaces** is connector-scoped ownership for Discord lifecycle channels (single-owner precedence), not a generic bot-wide property. Optional **`identities.discord.ingress`** sets **messages** (`none` | `routed` | `owned_spaces`) and **interactions** (`none` | `routed` | `own_messages` | `owned_spaces`). If omitted, defaults derive from YAML routing and **handlesOwnedSpaces**: routed bots use **routed** ingress for both; lifecycle owners without routing use **owned_spaces** messages and **own_messages** interactions so they do not publish duplicate general guild messages while still receiving component interactions on their posts; otherwise the gateway is **outbound-only** (no listeners). Top-level **discordTokenEnvKey** and **handlesOwnedSpaces** are **deprecated** (still accepted for backward compatibility); use `identities.discord.tokenEnvKey` and `identities.discord.handlesOwnedSpaces` instead. Optional top-level **defaultDiscordTokenEnvKey** is a **retained transitional** setting when a bot has no `identities.discord.tokenEnvKey`, not the preferred long-term identity model. Set the same env var names in `.env` with the actual tokens. The default config uses `identities.discord.tokenEnvKey` per bot (e.g. `LUNA_DISCORD_TOKEN`, `ARRIETTY_DISCORD_TOKEN`) so lifecycle rooms can use Arrietty's identity. Outbound delivery is abstracted by **ReplySender** (generic sender contract) and **OutboundGateway** (transitional gateway); core uses these interfaces; **Discord** implements both (**DiscordReplySender**, **DiscordGateway**). The **engine** holds a **connector-keyed reply sender map** and a **connector-keyed ReplyTargetResolver** registry; Bootstrap registers each connector’s sender via **setReplySender(connectorId, sender)** and the Discord resolver via **registerReplyTargetResolver("discord", new DiscordReplyTargetResolver())**. The engine **obtains ReplyTarget** only via the connector-owned resolver by connector id (source prefix); when no resolver is registered or the resolver returns empty, the engine does not deliver (fail closed); when delivering it uses **target.channelId()** and **target.messageId()**. When no sink is registered for the event source, the engine’s **fallback** uses the **source prefix** (e.g. the segment before `":"` in `sourceId`) to look up the sender—**no connector-specific literals** (such as `"discord"`) in the engine. Delivery is routed by **OutboundDeliveryRouter**: it resolves the sender from the delivery target and **lifecycle context** (`configuredBotId`). **getGatewayForChannel** returns the configured bot's gateway for lifecycle channels; if that bot has no gateway, it returns null (no fallback to default). The router exposes **getSelfUserIdForBot(botId)** for workflow actions (e.g. permission overwrites). **DiscordAppReplySink** casts to **DiscordGateway** when calling interaction-specific methods (e.g. defer, update), and deferred interaction follow-ups stay pinned to the ingesting bot's gateway when `ingestBotId` is present so bot-local deferred hooks are not lost to the default gateway. For lifecycle rooms, if the resolved bot has no registered sender (e.g. that bot's token was not set), the router logs an error and does not send—no silent fallback. Each bot can set `workflow.type` (for example `stub` or `configured`) plus runtime options such as `conversationMode` and `sessionKeyStrategy` (e.g. `thread` for feature-room bots—arrietty, architect, auditor, scribe—so conversation keys use thread id); Bootstrap creates a `WorkflowRunner` per bot via `WorkflowRunnerFactory`, and the engine uses `runResult(event, stateStore, botId)` to execute it. Routing filters support keys such as `discordTrigger`, `discordMention`, and `discordAuthors`; `discordMention` matches case-insensitively against normalized **user/bot** mention tokens: `@displayName` tokens in message text, numeric snowflakes from Discord `<@id>` / `<@!id>` markup (and the same ids from connector-provided mention metadata). Discord channel allowlists/excludes match either the event channel id or, for thread events, the parent channel id carried by the connector payload. **Role** pings (`<@&id>`) and angle-bracket text that is not a numeric user/bot id do **not** count; optional `discordAuthors` restricts which Discord users can trigger the bot: list entries can be a **numeric Discord user id** (stable, matches actorId) or a **username** (matches actorUsername, case-insensitive). For **ownership-based routing**, a bot can set **handlesOwnedSpaces: true** in config; when a Discord channel has a lifecycle context and that bot is the owner (configuredBotId), the Router returns only that bot for events in that channel (single-owner precedence), so e.g. Arrietty-owned rooms receive only Arrietty. Follow-up messages in the same session (e.g. without a mention) continue the workflow when the bot is waiting for input for that session key. For `configured`, use `workflow.params.workflowRef` to reference a workflow id from the YAML `workflows:` section, which defines a step DSL with `ask_input`, `prompt_for_field`, `capture_field` (optional `trimAndLower: true` or `transforms` list; when both present trimAndLower wins), `extract_event` (fromEvent: payload.\<key\>, context.\<field\>), `call_action`, `branch` (operators: equals, not_equals, blank, nonblank, contains, starts_with, regex, one_of; optional transform on state value), and `done`. **Rich interactions:** intent model (e.g. `intent: present_choices`, `confirm_action`) and step options (`choices`, `confirmLabel`, `cancelLabel`, `fields`); engine delivers replies via the connector **sink registry** (lifecycle operations: respondImmediately, sendFollowUp, updateMessage); **Discord lifecycle** is adapter-owned (ack/defer within platform window, auto-defer when needed). Channel replies use the gateway **send** overload so initial messages can include **components** (buttons, select menus) when the response has an intent (e.g. present_choices, confirm_action). See [Architecture](mkdoc/architecture.md) and [Discord](mkdoc/features/domain/connectors/discord.md) in the docs.

Configured workflows persist per-session `ConfigurableWorkflowState`. `WorkflowRunnerFactory` chooses `GraphWorkflowRunner` when a workflow defines `workflowSchema: v2` and a `phases` map; otherwise it uses `ConfigurableWorkflowRunner` (linear steps). `CallActionStep` prefers `ToolRunner` when a tool is registered and falls back to `WorkflowActionRegistry` for legacy actions; for tool-backed steps it also forwards event metadata and the session key so tools can launch external work and correlate replies. Runner failure logs now include phase/step, capability, and action context with the full throwable, and blank exception messages fall back to the exception class name so audits and Discord replies are never just `null`. After the workflow runs, the engine can invoke a bot reasoner with the workflow reply context, current session state, and the last normalized user message; any proposed tool calls are executed through `ToolRunner` under the bot's `ToolPolicy`. Session state may include **`workflowUnresolvedItemsJson`** (generic clarification ledger), **`workflowProgressEventsJson`** (deduped progress events), and v2 **`workflowDeliberationMetaJson`** when the workflow YAML defines **`deliberation`**. Planning correlates follow-ups with merge-closed ledger fingerprints and, after a merged clarification, can **selectively rerun** (skip expansion, one inner critique round) unless **`planningSelectiveRerunAfterClarification`** is `false`. **`deliberation.boundedClarificationChoices: true`** on a work profile opts into button-style **A or B** clarifications; default is plain text.

Example: Luna has `workflow.type: configured` with `workflow.params.workflowRef: luna_cursor` and a `discordMention: "luna"` routing rule (optionally `discordAuthors`). The shipped workflow is multi-turn: **guided repo selection** (choiceProvider `githubRepos` — GitHub API + "Use last repo" + "Custom repo"), code change prompt/capture, then a **confirmation step** (Launch / Edit repo / Edit request / Cancel). On Launch, Luna provisions the feature room and intake/spec thread, posts the handoff note, and calls `start_coordinator_planning` so `arrietty_room_v2` takes over inside the thread. Discord can show buttons or a select menu for choices. Edit repo and Edit request use branch steps with `clear` (clearKeys) so the runner clears those state keys before advancing, then reprompts for the cleared fields. Set `GITHUB_TOKEN` in `.env` for repo listing. Status, feedback, and PR links are reported back to Discord while the run is active.

**Lifecycle room (Phase 1):** Room and thread creation are **connector-owned** via **SpaceOperations** and **SpaceOperationsRegistry**; workflow actions (`create_channel`, `create_thread`) delegate to the connector capability by source prefix, and Bootstrap registers the Discord implementation (**DiscordSpaceOperations**). These actions **do not default to any connector**: capability lookup is **fail-closed**—if no **SpaceOperations** is registered for the event's source prefix, the action returns `CHANNEL_CREATE_FAILED` or `THREAD_CREATE_FAILED` (no implicit fallback). **SpaceOperations** returns typed results (**CreateRoomResult**, **CreateThreadResult**—success with id or failure with reason); **DiscordSpaceOperations** implements this contract. Workflow actions **create_channel** and **create_thread** translate those results to channel/thread id or sentinel (`CHANNEL_CREATE_FAILED`/`THREAD_CREATE_FAILED`) for `run()` so `storeIn` and branch steps continue to use id/sentinel. SpaceOperations uses request DTOs (**CreateRoomRequest**, **CreateThreadRequest**) with explicit intent fields; a request factory performs bind/state resolution; **DiscordSpaceOperations** uses only request getters (no raw map access). **CreateRoomRequest** may include optional **participantBotIds** (list of bot ids); when non-empty, DiscordSpaceOperations applies **permission overwrites** for each bot in the list (via `getSelfUserIdForBot(botId)`); otherwise a single **lifecycleOwnerBotId** is used for backward compatibility. **Arrietty-owned feature room:** Arrietty is the sole planning participant and coordinator. **Arrietty = Orchestrator**: bot id remains `arrietty`; primary coordinator in feature rooms. The **Arrietty** bot in `config/bots.yaml` is the template for per-channel lifecycle room instances; it has `workflowRef: arrietty_room_v2` as the sole production planning lifecycle and `identities.discord.handlesOwnedSpaces: true` so it owns inbound events in channels it provisions. Legacy message-first room workflows can still begin with `capture_field` plus a branch step. For `branch`, blank/empty state is not truthy; use `when: { key, value: "" }` to match blank input explicitly. When a channel has a lifecycle context but the owner bot does not have `handlesOwnedSpaces`, the Router **logs a warning** and uses filter-based routing instead of single-owner. Luna’s workflow uses the full provisioning sequence: `create_channel` (Discord gateway `createTextChannel`; returns channel id or `CHANNEL_CREATE_FAILED` on failure; room name is derived from state when not provided—repo segment is the **repository name only**, no owner/username—and **normalized** to Discord-safe format before create). For Arrietty-owned planning rooms use **participantBotIds** in bind (e.g. `participantBotIds: [arrietty]`); else **lifecycleOwnerBotId** for single-owner; after create, permission overwrites are applied for each. **Room vs thread routing (feature rooms):** **FeatureRoomStateStore** indexes **roomChannelId** and **intakeThreadId**; **`PlanningIntakeBindingResolver`** also consults **`FeaturePlanStateStore`** so intake threads and coordinators align when plan state records **`intakeThreadId`** or supplements room indexing. On the **room channel**, **Router** returns only the **primary coordinator** (participant with **primaryCoordinator**, else **ORCHESTRATOR**’s **configuredBotId**) for low noise. On the **intake/spec thread** id, **Router** returns the **primary coordinator** for **messages** and **component interactions** when that thread is the planning intake (single planning ingress). While planning is **exclusive** on that thread, **`Router.route`** returns only the coordinator—YAML filter matches for other bots are skipped—and **VinekeepersEngine** does not merge in extra bots from **waiting Discord sessions** on those messages, so incidental plain text does not start sibling workflows there. **post_channel_message** uses **asBotId** before **asRole** before the default reply path; with **OutboundDeliveryRouter**, **sendAsExplicit** / **sendAsRoleExplicit** enforce strict resolution (invalid **asRole** or missing participant yields an error return, no silent fallback). Non-explicit **sendAs** / **sendAsRole** on the router may still fall back to the default sender when role lookup fails. Workflow state key **featureRoomParticipants** is produced by **provision_room_participants** (storeIn: featureRoomParticipants) and consumed by **initialize_feature_room_state** (when featureId/featureSlug missing, generates featureId = feat- + 12 hex and featureSlug from initialRequest/repo sanitized; preserves when supplied; builds **FeatureRoomState** in **FeatureRoomStateStore**). **FeatureRoomStateStore.getParticipantBotIds** orders participants by **PlanningRole.ordinal()** for workflow-driven sends. When **Router** does not match a feature-room channel or thread, it uses legacy single-owner routing via **LifecycleContext**. Then: branch on `channelId == CHANNEL_CREATE_FAILED` → **provision_bot_instance** (Arrietty) → **create_lifecycle_context** → **create_thread** (lifecycle owner gateway; storeIn deliveryChannelId) → **provision_room_participants** (storeIn: featureRoomParticipants) → **initialize_feature_room_state** → **initialize_feature_plan_state** → **ensure_repo_workspace** → **upsert_artifact_section_data** (requirements narrative) → **post_channel_message** (intake/spec handoff, `target: thread`) → **start_coordinator_planning** (in-process kickoff so `arrietty_room_v2` begins in the thread without a user wake-up message; idempotent). If the kickoff fails, or produces neither a reply nor a recorded kickoff side-effect post, the engine marks the thread session as failed and posts a fallback internal-error notice instead of silently returning success. **launch_cursor_run** runs later inside **arrietty_room_v2** after approval. After a successful **create_channel**, the workflow continues with **provision_bot_instance** (branch target includes that step). Optional env: **VINEKEEPERS_REPO_WORKSPACE_ROOT**, **VINEKEEPERS_ALLOW_GIT_CLONE**, **GIT_EXECUTABLE** for local clone behavior in **ensure_repo_workspace**. The shipped Luna success **done** message points operators to the intake/spec thread: `"Feature room is ready. Continue in the **intake/spec** thread (<#{{deliveryChannelId}}>) to finish the plan, get approval, and launch."` For **call_action** steps, **bind has precedence over state** for action inputs. `post_channel_message` send target is **deliveryChannelId or channelId** (bind then state), or explicit **target: room | thread** or **targetChannelId** (channel or thread id); if target is thread and `deliveryChannelId` is the `THREAD_CREATE_FAILED` sentinel, it falls back to channelId. It interpolates **content** from a merged map (state then bind; bind overrides), e.g. `lifecycleBotName` in bind; optional **asRole** or **asBotId** in bind selects which participant's sender is used for delivery. **`launch_cursor_run` is the authoritative launch path** for approved coordinator flows; it returns an acknowledgement that includes repo/branch/agent URL and optional **status** (e.g. "Status: launching"); `cursor.fullRun` is not used in the luna_cursor flow. The Cursor run prompt is built by **`CursorInstructionComposer`** (single source; includes /nova-code). **`CursorCloudRunMonitor`** polls Cursor for run status and feedback and relays updates (running state, PR URL, final summary) to Discord; when **LifecycleRunRecord** has **deliveryChannelId** set, it sends to that thread (messageId null). `LifecycleContext` is extended with `configuredBotId`, `runtimeBotInstanceId`, optional `repo`/`requestText`, and optional **deliveryChannelId** (thread id; `THREAD_CREATE_FAILED` excluded from context). **OutboundDeliveryRouter** resolves the sender via **LifecycleContextStore.getByDeliveryTargetId** (channel or thread id) or **FeatureRoomState** when sending as a role; if that bot's sender is unavailable (e.g. no token), lifecycle delivery fails clearly (error log, no send). `LifecycleRunRecord` and `LifecycleContext` (in `LifecycleContextStore`) track runs and context by channelId and externalRunId; the store also indexes by delivery target id for router lookups. **FeatureRoomStateStore** holds FeatureRoomState by channel and delivery target for feature-room routing and sendAs/sendAsRole. `post_channel_message` sends to the channel (or thread when deliveryChannelId is set) from workflow state after creating the lifecycle room.

**Work profiles:** Optional `config/work-profiles.yaml` defines declarative artifact/section schemas (default profile `software_feature_planning` still carries declarative readiness gates for review-packet substance; feature rooms use **`software_feature_planning_v2`** with request exploration, current-state grounding, and richer approval artifacts). Bootstrap loads profiles into `WorkProfileRegistry`. Production Arrietty planning now has one authoritative spine: **workspace preflight** (`PlanningWorkspacePreflightService`) → **silent synthesis** (`SilentPlanningSynthesisService`) → **room evaluation** (`PlanningEvaluationService` returning a finalized `PlanningEvaluationDecision`) inside **`PlanningCyclePipeline`** → deterministic routing to **one question**, **another silent synthesis pass**, or **packet/critique/readiness/approval**. `coordinatorClarification.mode: canonical_v1` remains only as the clarification transport contract (single question / merge metadata). `FeaturePlanState` is the canonical planning truth, and packet/critique/readiness/approval stay downstream of evaluation-authorized readiness.

### Coordinator planning: what Arrietty is asking (readiness vs approval)

- **Strict clarification contract** — Before drafting, the live path interrupts only for true **workspace** blockers. After silent synthesis, **one structured `PlanningEvaluationService` call** reads canonical plan state plus repo/context grounding and returns the gap list, confidence, one optional best question, assumptions/issues/risks/decisions to add, and `ready_for_packet`. Code enforces the guardrails: no question when `ask_user_required` is false, at most one question when it is true, no `ask_user_required` without a valid primary ask gap, and no packet while workspace blockers, blocking gaps, or structured drafting failures remain. `merge_planning_clarification_choice` still requires the `planningClarificationMetaJson` `gapId` + `mergeTargetPath` contract, and the live path routes only from the canonical evaluation result.
- **Question visibility** — Arrietty `prompt_for_field` asks in the intake/spec thread are prefixed with **`❓`** so clarification, readiness, and approval questions stand out in chat.
- **JSON resilience** — **`run_request_expansion_llm`**, **`run_llm_planning_synthesis`**, and coordinator role passes now share the same object-only JSON extraction / repair path in **`PlanningLlmJsonSupport`**. Transport errors, unreadable JSON, schema-rejected upserts, and empty no-op responses are classified explicitly; when a prior draft is recoverable, the flow can continue from the saved draft with explicit failure metadata instead of inventing a second semantic branch. When a **repo checkout path** or non-empty **`planningRepoEvidenceJson`** snapshot is present, the expansion context JSON also carries **`planner_instruction`**, nudging **observed** repo evidence and **concrete impacted components** instead of generic repo-agnostic planning.
- **Readiness checkpoint (`REVIEWABLE` / “Ready for review”)** — After the planning packet is posted, the bot may stop for a **planning review checkpoint** before launch approval opens. This checkpoint appears only when the packet is reviewable: the full packet is visible, critique has completed, there is no outstanding clarification ask, and machine blockers have already been converted into revision work instead of silent approval-ish copy. **Continue to approval** means: check whether the packet is truly eligible to open **Approve / Approve with risks / Revise / Reject**. **Revise plan first** means: run **another planning round** to strengthen the draft **before** that approval gate. If the action menu does not render, reply with `continue` or `revise` instead of looking for buttons.
- **Plain-language review copy** — Discord planning/review messages use **`PlanningUserFacingCopy`** (and profile hints via **`PlanningPromptFormatter`**) so users see short English labels for readiness, critique severity, and related statuses. Workflow branches and persisted plan state still use the machine values (e.g. **`planReadinessStatus`**, **`MUST_FIX`**).
- **Decision log rows** — When the workflow asks for a **Decision** entry (repeatable decision log), the prompt is framed as an explicit **question** about the decision itself instead of sending you to a numbered cross-reference. It still asks for **what you decided**, **why** (constraints or context), and **what that implies** (trade-offs, follow-ups, or options ruled out), and it says your reply is **saved on the plan** so it does not read like an unexplained status line. Hints come from `config/work-profiles.yaml` via **`PlanningPromptFormatter`**; the readiness fork uses **`planReadinessCheckpointGuide`** from **`PlanningUserFacingCopy`** in addition to **`planReadinessStatusLabel`**.
- **Planning packet layout (Discord)** — **`PlanningThreadPacketFormatter`** renders the posted packet with **Discord-friendly labeled list items** for tracked **assumptions**, **issues**, **risks**, **decisions**, and **open questions**. Instead of table columns, each item spells out fields such as **Priority**, **Status**, **Severity**, **Impact**, and **Likelihood** inline so the packet stays readable in Discord. When **user stories** or **acceptance criteria** contain at least two bullet or numbered lines, an additional numbered **list** block is appended under those sections. Long narrative fields are **soft-truncated** per section with an explicit italic footnote *"(Truncated for display length.)"*; inline item text that exceeds a display budget ends with **…**. Empty sections show **`_Not drafted yet._`** or **`_None recorded._`** as appropriate.

## Documentation

Docs (MkDocs) use the configured docs root in `.cursor/project.yml` (`paths.docs_dir`, currently `mkdoc`). To build and serve the docs locally (including Mermaid diagrams on the Architecture page), install the docs stack then run MkDocs from the project root:

```bash
pip install -r requirements-docs.txt
mkdocs serve
```

Then open http://127.0.0.1:8000 (or the URL MkDocs prints).

## Environment

The app loads a `.env` file (if present) into system properties at startup. A sample contract lives in `.env.example`.

Required for Luna on Discord:

- **Discord token:** Set env vars whose *names* match the keys in `config/bots.yaml`: each bot's `identities.discord.tokenEnvKey` (e.g. `LUNA_DISCORD_TOKEN`, `ARRIETTY_DISCORD_TOKEN`, `GADGET_DISCORD_TOKEN` for the default config), or top-level `defaultDiscordTokenEnvKey` when a bot has no identity key. Put the actual token values in `.env`; never commit raw tokens or put them in config. If a bot's env var is blank, that bot is skipped for Discord. In the [Discord Developer Portal](https://discord.com/developers/applications), open your app → Bot → **Privileged Gateway Intents** and enable **Message Content Intent** (required for reading message text and mentions).
- `CURSOR_API_KEY`: Cursor API key used for Cloud Agent launches and status polling.

Optional:

- `HEALTH_PORT`: port for the health HTTP server (default 8080); used by Prometheus uptime bridges on Docker network **`monitoring`** (`/health`, `/`). Set to 0 or omit to disable. Create **`docker network create monitoring`** and use `compose.yaml`’s **`monitoring`** network so `~/Docker/prometheus` can reach **`vinekeepers:8080`**.
- `CURSOR_API_BASE_URL`: defaults to `https://api.cursor.com`
- `CURSOR_MODEL`: explicit model id for cloud launches
- `CURSOR_BASE_BRANCH`: default base branch when Luna launches a run
- `CURSOR_POLL_INTERVAL_MS`: how often Vinekeepers polls Cursor for feedback updates
- `CURSOR_HTTP_CONNECT_TIMEOUT_MS` / `CURSOR_HTTP_REQUEST_TIMEOUT_MS`: optional HTTP client connect and per-request timeouts for Cursor Cloud API calls (omit for library defaults)
- `VINEKEEPERS_REPO_WORKSPACE_ROOT`: directory for shallow git clones (default on host: Java temp dir; **Dockerfile default: `/app/checkouts`**)
- `VINEKEEPERS_ALLOW_GIT_CLONE`: `true` to allow **ensure_repo_workspace** to clone remote repos (default: false; local checkouts still resolve when the repo path is an existing git directory)
- `VINEKEEPERS_REPO_WORKSPACE_FORCE_REFRESH`: `true` to skip reuse and force a fresh materialization path for **ensure_repo_workspace** when cloning is enabled (default: false)
- `GIT_EXECUTABLE`: git binary name/path for workspace resolution (default: `git`)
- `OPENAI_PLANNING_DISCORD_PROGRESS`: when not `false` (default), posts a short **Update:** message to the workflow channel when each instrumented OpenAI planning call starts (same targeting as other lifecycle posts via `post_channel_message`).
- `OPENAI_LOG_PLANNING_BODIES`: when not `false` (default), logs truncated, redacted **system**, **user**, and **assistant** bodies for those calls at INFO; set to `false` to keep only outcome lines for failures and success summaries.
- `OPENAI_LOG_BODY_MAX_CHARS`: max characters per logged prompt/response fragment (default `4096`, clamped between 256 and 32768).
- **Planning RAG (optional):** `VINEKEEPERS_PLANNING_RAG` — set `false` to skip **`prep_planning_repo_grounding`**. For vector grounding, set **`QDRANT_URL`** or **`VINEKEEPERS_QDRANT_URL`** (Qdrant HTTP API base) and **`OPENAI_API_KEY`** for embeddings. Optional: **`QDRANT_API_KEY`** / **`VINEKEEPERS_QDRANT_API_KEY`** (often unset for local Qdrant), **`QDRANT_COLLECTION`** (default `vinekeepers_planning_grounding`), **`OPENAI_EMBEDDING_MODEL`** (default `text-embedding-3-small`), **`OPENAI_EMBEDDING_DIMENSIONS`** (default `1536`; must match the model), **`PLANNING_RAG_EMBED_BATCH_SIZE`**, **`PLANNING_RAG_MAX_CHUNKS`**, **`PLANNING_RAG_TOP_K`**. If Qdrant URL or the OpenAI key is missing, planning continues without RAG.

## Logging and troubleshooting

Cursor API failures are visible in application logs (WARN level: transport exceptions and non-2xx responses with status, error code, and message) and surface as `CursorCloudException` with messages suitable for debugging (e.g. missing key, request/response errors). At DEBUG level the adapter logs safe per-request diagnostics (URI, key configured, model, repo, branch) without secrets. When no bot matches an event, the router logs at **INFO** with a structured line: source, kind, channelId, parentChannelId, authorId, actorUsername, mentions, ingestBotId, `rolePingDetected`, `routingHint`, and a truncated **textPrefix**—use this to troubleshoot routing (e.g. discordAuthors or discordMention not matching, or a role ping being used where a direct bot mention is required).

OpenAI-compatible **planning** calls that supply call context log a completion line at INFO (duration, model, activity label) and, unless **`OPENAI_LOG_PLANNING_BODIES=false`**, truncated redacted copies of the system prompt, user message, and assistant reply. Discord shows an **Update:** line at call start when **`OPENAI_PLANNING_DISCORD_PROGRESS`** is enabled (default).

## Cursor / skills

Spec and code workflow rules live under `.cursor/rules/`. Reusable skills (e.g. update-readme, run-tests, update_tests, static-analysis) are under `.cursor/skills/` (common, nova-code, vinekeepers-code, etc.). The nova-code workflow (`.cursor/workflows/nova-code.yml`) runs guardrails (orchestrator-applied), update_tests, update_readme, and when `specs/specs.yml` exists, schema/drift gates and specs bootstrap.

Cloud runs should also follow the repo-level guidance in `AGENTS.md`, which summarizes the spec workflow, validation commands, and documentation expectations for Cursor Cloud Agents.
