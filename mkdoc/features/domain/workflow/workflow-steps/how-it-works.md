# How it works

# Overview

Configured workflows are defined by `WorkflowDefinition` and executed as ordered `WorkflowStep` instances. Each step returns a `StepResult` with a `StepOutcome`, optional stored values, and next-step information so the runner can continue, wait, branch, complete, or surface an error.

# Flow

1. Config loads a `WorkflowDefinition` with ordered step configs.
2. `ConfigurableWorkflowRunner` resolves each config into a concrete step implementation.
3. A step executes and returns `StepResult` describing the next outcome.
4. The runner stores state updates, advances, waits, branches, or completes based on `StepOutcome`. For `branch` steps, blank or empty string values are not truthy; use value-based `when: { key, value: "" }` to route on blank input.
5. Coordinator planning paths that call **`OpenAiChatClient`** with a non-blank **`OpenAiCallContext.activitySummary`** (from **`run_request_expansion_llm`**, **`run_llm_planning_synthesis`**, **`StructuredLlmArtifactUpsertPass`**, and related wiring) invoke **`OpenAiPlanningProgressSink`** immediately before each HTTP completion; production **`Bootstrap`** registers **`OpenAiPlanningProgressPoster`**, which posts Discord lines prefixed with **`Update:`** (markdown bold in the rendered message) via **`post_channel_message`** unless **`OPENAI_PLANNING_DISCORD_PROGRESS`** is false. The same client logs per-call duration at INFO and, when **`OPENAI_LOG_PLANNING_BODIES`** is not false, truncated `sk-*`-redacted system, user, and assistant text (or a failure hint), capped by **`OPENAI_LOG_BODY_MAX_CHARS`**.
6. Optional **planning RAG:** When ingress YAML includes **`legacy_action: prep_planning_repo_grounding`** after **`ensure_repo_workspace`**, **`PrepPlanningRepoGroundingAction`** delegates to **`PlanningRepoGroundingService`**: load prior **`.vinekeepers/repo-grounding.parquet`**, chunk files under the materialized checkout, embed only chunks whose content hash is not yet cached, upsert vectors into Qdrant with payload scoped by repo ref and branch, write merged Parquet, and spread **`planningRag*`** diagnostics plus **`planningRagRetrievalText`** when search succeeds. **`spread_plan_workspace_signals`** merges selected **`planningRag*`** keys into **`planningRepoEvidenceJson`**. **`run_llm_planning_synthesis`** includes retrieval text in the synthesis prompt when **`planningRagAvailable`** is true. If **`VINEKEEPERS_PLANNING_RAG`** is false or Qdrant/OpenAI configuration is unusable, the action continues without failing the graph.
7. **Planning cycle evaluation:** Each cycle runs **`PlanningWorkspacePreflightService`** first, then **`SilentPlanningSynthesisService`** (expansion, role passes, synthesis, artifacts, depth). After silent synthesis, **`PlanningCyclePipeline`** builds the evaluation context and **`PlanningEvaluationService`** performs one structured LLM evaluation over canonical plan state, returning a finalized **`PlanningEvaluationDecision`** with confidence, canonical gaps, one optional best question, AIRD deltas, readiness, block reason, and canonical next action. The pipeline applies those deltas deterministically, projects one clarification through **`CanonicalClarificationSpreadBuilder`** / **`ClarificationProjection`** when `ASK_USER` is authorized, persists the canonical decision, and routes only through **`PlanningCanonicalDecisionSupport`** projection. `merge_planning_clarification_choice` validates `gapId` + `mergeTargetPath` in meta against the canonical merge contract, accepts either button ids or plain-text replies with best-effort interpretation, and routes the next pass back through silent synthesis. Production enforces one-question max, fail-closed invalid evaluation handling, and no ready-for-packet route while blocking gaps remain.
8. **Request expansion LLM:** **`run_request_expansion_llm`** may include a **`planner_instruction`** field in the user JSON when a workspace checkout path or non-trivial **`planningRepoEvidenceJson`** is present, nudging the model toward observed repo evidence and grounded components before deterministic **`build_request_exploration`**.

# Inputs and outputs

- **Inputs:** Workflow definition, current configurable workflow state, event payload (including interaction payload: interactionId, token, customId, values when kind is interaction), and optional registered actions or tools.
- **Outputs:** Step outcomes, stored state values, next-step selection, optional reply text, and optional `OutboundResponse` (richReply with `ResponseIntent`) for the engine to deliver via the connector sink.
- **Planning OpenAI observability (env):** **`OPENAI_PLANNING_DISCORD_PROGRESS`** (default true), **`OPENAI_LOG_PLANNING_BODIES`** (default true), **`OPENAI_LOG_BODY_MAX_CHARS`** (default 4096, clamped 256–32768), plus existing planning API keys documented under the **env** feature and **README** / **`.env.example`**.
- **Planning RAG (env):** **`VINEKEEPERS_PLANNING_RAG`**, Qdrant URL/key/collection, embedding model/dimensions, **`PLANNING_RAG_EMBED_BATCH_SIZE`**, **`PLANNING_RAG_MAX_CHUNKS`**, **`PLANNING_RAG_TOP_K`** — see **env** feature **contracts** and **`.env.example`**.
