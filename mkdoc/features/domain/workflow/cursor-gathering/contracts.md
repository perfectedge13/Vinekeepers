# Contracts

# APIs

This feature calls the official Cursor Cloud Agents API:

- `POST /v0/agents`
- `GET /v0/agents/{id}`
- `GET /v0/agents/{id}/conversation`
- `POST /v0/agents/{id}/followup` (supported by the adapter contract)

# Schemas

Luna configuration in `config/bots.yaml` supplies bot routing, `workflowRef: luna_cursor`, and the ordered gathering steps. `ConfigurableWorkflowState` stores the conversational gather state, while `LifecycleRunRecord` stores the launched run identity and Cursor feedback snapshot.

# Cursor adapter behavior

- **Authentication:** `Authorization: Bearer <CURSOR_API_KEY>`; launch fails fast when `CURSOR_API_KEY` is not configured.
- **Request payload:** Serialized with Jackson `NON_NULL` so null fields are omitted (avoids API errors).
- **Non-2xx handling:** `extractErrorMessageAndCode` parses: error as string, nested `error.message`/`error.code`, top-level `message`, plain text body, or empty body (generic message with status).
- **Diagnostics:** At DEBUG, logs safe per-request data (URI, key configured, model, repo, branch); never logs API key, request body, or full response body.
- **HTTP timeouts (optional):** **`CURSOR_HTTP_CONNECT_TIMEOUT_MS`** and **`CURSOR_HTTP_REQUEST_TIMEOUT_MS`** configure **`HttpClient`** connect timeout and per-request timeout when set (see **`.env.example`**).

# Lifecycle room (Phase 1)

- **`LifecycleContext`:** run context with channelId, externalRunId, configuredBotId, runtimeBotInstanceId, optional repo/requestText, and optional deliveryChannelId; **withDeliveryChannelId(id)** returns new instance with that delivery target for store updates after create_thread; indexed by channelId and externalRunId.
- **`LifecycleContextStore`:** store and resolve lifecycle contexts by key (e.g. channelId, externalRunId); **setDeliveryTargetId(contextId, deliveryTargetId)** updates context delivery target (ignores null, blank, THREAD_CREATE_FAILED); used by create_thread after success.
- **`RuntimeBotInstance`:** provisioned bot instance (generic instanceId, templateBotId, displayName, channelId); e.g. Arrietty template.
- **Coordinator-owned feature room:** **FeatureRoomState** and **FeatureRoomStateStore** hold participant state by channel and delivery target. **FeatureRoomStateStore.getParticipantBotIds** returns participant configuredBotIds in stable **PlanningRole.ordinal()** order. **featureRoomParticipants** is a transient workflow handoff (List&lt;Map&gt;; role, configuredBotId, runtimeBotInstanceId, displayName optional default, primaryCoordinator) from **provision_room_participants** to **initialize_feature_room_state**, which validates the single-coordinator room contract and persists typed participants. **provision_room_participants** must resolve the orchestrator template/configured bot id from bind or state (**orchestratorConfiguredBotId**, **templateBotId**, valid **instanceId**’s **RuntimeBotInstance.templateBotId**, or **__botId**); **Bootstrap** passes **BotCatalog** so **displayName** can default from the loaded bot’s persona. **Response policy:** Router returns the primary **coordinator** configuredBotId for **intake/spec thread messages** and **component interactions** when that id resolves. The **room channel** routes to the primary **coordinator** only. Thread collaboration uses explicit **post_channel_message** steps with **asRole**/**asBotId** (precedence: asBotId over asRole; strict errors when explicit sender cannot resolve via **sendAsExplicit** / **sendAsRoleExplicit**). **JDA:** interaction events include **threadId** in the payload when the channel is a **ThreadChannel**, matching **message** events so **sessionKeyStrategy: thread** resolves the same session key for buttons as for thread messages.
- **Workflow actions (call_action):** Bind has precedence over state for action inputs. **SpaceOperations** returns typed **CreateRoomResult**/ **CreateThreadResult**; actions translate to id or sentinel for `run()`. `create_channel` builds **CreateRoomRequest** via **CreateRoomRequest.from(Event, state, bind)**; optional **participantBotIds** (list) or **lifecycleOwnerBotId**; delegates to **SpaceOperations.createRoom**; Discord applies permission overwrites for each participant. **provision_room_participants** (storeIn: featureRoomParticipants) provisions only the orchestrator coordinator participant into state (see bind keys above). **initialize_feature_room_state** builds **FeatureRoomState** from featureRoomParticipants and puts it in **FeatureRoomStateStore**; when featureId/featureSlug are missing, generates featureId = feat- + 12 hex and featureSlug from initialRequest/repo sanitized; preserves when supplied. **post_channel_message** send target: **deliveryChannelId** or **channelId** (bind then state), or explicit **target: room | thread** or **targetChannelId** (channel or thread id); THREAD_CREATE_FAILED fallback to channelId. Supports **asRole** or **asBotId** with precedence **asBotId** over **asRole** over default send; explicit paths use **sendAsExplicit** / **sendAsRoleExplicit** (errors when unresolved). `create_thread` builds **CreateThreadRequest**; delegates to **SpaceOperations.createThread**; uses lifecycle owner gateway when channel has context; on success **LifecycleContextStore.setDeliveryTargetId**(contextId, threadId); `storeIn` e.g. `deliveryChannelId`. Branch on `channelId == CHANNEL_CREATE_FAILED` to done. In the shipped Luna handoff, the sequence is **`provision_bot_instance`** → **`create_lifecycle_context`** → **`create_thread`** → **`provision_room_participants`** → **`initialize_feature_room_state`** → **`initialize_feature_plan_state`** → **`ensure_repo_workspace`** → **`upsert_artifact_section_data`** → **`post_channel_message`** (thread handoff) → **`start_coordinator_planning`**. `launch_cursor_run` happens later from the coordinator-owned **`arrietty_room_v2`** approval path, not directly inside Luna’s post-confirm provisioning sequence. The done step may point operators at the intake/spec thread (for example the shipped `"Feature room is ready..."` message using **`deliveryChannelId`**).
- **`CursorInstructionComposer`:** single source for Cursor run instruction text (repo, baseBranch, change); includes /nova-code; used by `LaunchCursorRunAction` and `CursorFullRunTool`.

# Phase B (structured discovery)

- **Prepare phase (production v2):** In **`arrietty_room_v2`**, **`planning_prepare`** is workspace-only. It runs **`spread_planning_workspace_blocker`** and, only when repo workspace resolution is blocked, a single **`prompt_for_field`** / **`capture_field`** / **`classify_assumption_or_issue`** / **`ensure_repo_workspace`** loop until the blocker clears, then **`recompute_plan_progress`** → **`mark_intake_discovery_complete`**. Production v2 does **not** run proposal generation, proposal confirmation, or generic missing-field prompting inside **`planning_prepare`**.
- **Structured discovery loop (legacy / tests):** For paths that still wire it: **`get_structured_discovery_gaps`** (storeSpread) → branch on **`discoveryHasOpenGaps`** → **`build_insight_discovery_agenda`** (storeSpread; **ClarificationPromptQualityGate**; legacy **`build_discovery_agenda`**) → optional **`prompt_for_field`** / **`capture_field`** → **`capture_and_apply_discovery_answer`** → **`classify_assumption_or_issue`** → **`recompute_plan_progress`** → branch until no open gaps or **`discoveryBlockingIssueMode`**. **Production v2** does **not** run this loop inside **`planning_prepare`**, and intake blocking clarification now surfaces **workspace blockers only**. **Post-draft canonical clarification:** after **`planning_autonomous_draft`**, phase **`planning_assess_clarification`** runs **`planning_finalize_cycle_spread`** and routes on **`planningCanonicalNextAction`** for v2 rules (**`rs_post_draft`**). When the work profile sets **`coordinatorClarification.mode: canonical_v1`**, **`coordinatorClarification.engine`** supplies **`maxClarificationTurns`**, **`maxAutonomousRedraftsBeforeAsk`**, **`clarificationConfidenceThreshold`**, **`repoEvidenceAskThreshold`**, **`clarificationAskPriorityThreshold`**, **`allowAssumeAndContinue`**, and **`allowClarificationAfterCritique`**. Production uses **`CanonicalPlanningGapEngine`**, **`PlanningConfidenceService`**, and **`CanonicalGapResolutionPolicy`** (with **`CoordinatorClarificationGapEvaluator`** for open gaps) — **not** **`ClarificationEngineAssessor`**. **`PlanningMaterialCyclePacing`** separates material redraft/post routing from gap resolution. Once thresholds and loop caps are satisfied, the governor exits via **continue** or **block** instead of reopening generic fallback questions. Persisted plan fields include **`clarificationTurnsCompleted`**, **`clarificationOutcomeHistory`**, **`clarificationCoordinatorLedgerJson`**, and optional **`planningGapAskCountsJson`** / **`planningConfidenceBreakdownJson`**. **Contract:** packet **open questions** come from **unresolved** plan state, not LLM-generated lists, proposal payloads, or packet-backlog artifacts; internal failures are not surfaced as raw errors in user-facing thread copy.
- **Support and actions:** **`StructuredDiscoverySupport`** derives gaps from **`FeaturePlanState`** and the work profile, builds **`DiscoveryAgenda`** / **`DiscoveryQuestion`**, and exposes JSON and branch flags for workflow state. Actions map to `call_action` names above; **`classify_assumption_or_issue`** uses simple text rules to call **`append_plan_issue`** or **`append_plan_assumption`**.
- **Planning models:** Typed **`DiscoveryGap`**, **`DiscoveryQuestion`**, **`DiscoveryAgenda`**, and **`DiscoveryFinding`** live under `com.vinekeepers.state.planning` (REQ-STATE-001); JSON-serializable for workflow snapshots.

# Phase C (pre-launch critique and approval)

- **Placement:** After Phase B converges (or exits on blocking gaps), **`run_plan_critique_and_readiness`** (`storeSpread`) merges pre-approval visibility keys **`planningThreadReviewBody`** / **`planningThreadReviewBuildError`** (same content as **`build_planning_thread_review_body`**) and normalizes critique findings back into the same canonical decision object used post-draft. Workflow branching must use canonical decision projections (`planningCanonicalNextAction`, canonical intake stage, review/approval flags) only. **Canonical intake stage:** **`PlanningIntakeStage`** is advanced by **`coordinator_intake_bootstrap`**, **`mark_intake_discovery_complete`**, explicit v2 phase stage actions, and launch success/failure persistence; critique adds **MUST_FIX** (**`INTAKE_DISCOVERY_INCOMPLETE`**) while the stage is still **`GATHERING_CONTEXT`**. For the review checkpoint, proceed path uses **`acknowledge_readiness_human_decision`** only after the human explicitly chooses to continue. Standalone **`build_planning_thread_review_body`** remains registered for legacy YAML.
- **Actions:** **`run_plan_critique_and_readiness`** persists **`PlanCritiqueSnapshot`** and **`PlanConfidence`** on **`FeaturePlanState`** (**confidenceScore**, **confidenceReasons**, **structuredKnownFactCount** / **materialUnknownCount** / **materialUnknownLabels** reflecting known-vs-unknown planning facts), plus a canonical post-critique decision. It spreads **`planReadinessStatus`** (machine value for workflow branches), **`planReadinessStatusLabel`** (plain English for **`post_channel_message`** templates), **`planningCanonicalActionLabel`**, and **`planningCanonicalActionSummary`** as copy projected from the canonical decision. **`planReadinessCheckpointGuide`** is present only when status is **`REVIEWABLE`**; the explanatory copy is distinct from the later interactive prompt and now includes a truthful text fallback (`continue` / `revise`) instead of always promising buttons. The action also spreads **`planReadinessSummary`** (detail counts only; status is not duplicated in notes), **`planCritiqueSummary`**, **`planCritiqueFindingsJson`**, **`planConfidenceLevel`**, plus **`planningThreadReviewBody`** / **`planningThreadReviewBuildError`** from artifact sections (**overall_plan** / **validation_plan** / **project_context**) only when the canonical decision allows review or approval copy. **`hydrate_planning_session`** restores canonical decision projections together with **`planReadinessStatusLabel`** and **`planReadinessCheckpointGuide`** from persisted confidence. **`evaluate_planning_approval_gate`** requires posted-packet metadata, depth, **`READY`** readiness or acknowledged **`CONDITIONALLY_READY`**, **confidenceScore** ≥ **`PlanReadinessCalculator.APPROVAL_CONFIDENCE_THRESHOLD`** (**0.85**) when persisted, and canonical intake/clarification posture (**`PlanningIntakeStage`** past context-only phases and/or **`FeaturePlanState.autonomousPlanningPassCompleted`**, no pending coordinator clarification per **`PlanningApprovalGateSupport`**)—not merely a legacy **`humanDiscoveryCompleted`** spread in isolation. **`persist_plan_approval`** maps **`planApprovalDecision`** (`approve`, `approve_with_risks`, `revise`, `reject`) to **`PlanApproval`** with **`authorId`** from **`__event`**. **`LaunchCursorRunAction`** when **`FeaturePlanStateStore`** is wired and **`contextId`** is set requires **`PlanApproval`** status **`APPROVE`** or **`APPROVE_WITH_RISKS`** unless **`CURSOR_LAUNCH_SKIP_APPROVAL_GATE=true`**; always returns spread keys for launch outcome messaging.
- **Support:** **`PlanCritiqueSupport`** (rule-based findings), **`PlanReadinessEvaluator`** (packet-posted inference facade), **`PlanReadinessCalculator`** (evidence **`PlanConfidence`** + **0.85** approval bar shared with **`PlanningApprovalGateSupport`**).
- **Packet and depth gate copy:** **`PlanningThreadPacketFormatter`** (full packet for **`post_planning_packet_thread`**) and **`PlanningPacketDepthEvaluator`** / **`GenericReadinessEvaluator`** use **`PlanningUserFacingCopy`** (and work-profile titles) for Discord-visible section lines and gate-failure explanations instead of raw artifact paths, field ids, or internal enum tokens. **`derive_plan_governance`** (**`PlanGovernanceDeriver`**) feeds those labeled lists by merging gap-derived rows with artifact-sourced decision/open-question text and de-duplicating unresolved-question lines; open-question rows in the packet use **`PlanningArtifactTexts.substantiveUnresolvedQuestionLines`** so meta/completeness lines do not appear. **`build_planning_thread_review_body`** and **`build_role_planning_thread_messages`** share the packet formatter's labeled-list and truncation conventions where applicable (explicit truncation messaging when content is capped).

# Interfaces

- **`CursorCloudAdapter`:** abstraction over Cursor Cloud Agent launch, status, conversation, and follow-up operations.
- **`CursorFullRunTool`:** tool surface that launches the remote run and stores `LifecycleRunRecord`.
- **`CursorCloudRunMonitor`:** polling component that turns Cursor state changes into Discord replies.
- **`CursorCloudGatheringWorkflow`:** legacy workflow class retained for tests while production uses the configured flow.
