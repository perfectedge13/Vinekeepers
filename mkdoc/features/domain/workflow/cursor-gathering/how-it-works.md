# How it works

# Overview

The shipped Luna flow is configured in `config/bots.yaml` as workflow `luna_cursor`. Routing activates the `luna` bot from `discordMention: luna` (and optional `discordAuthors` to restrict which Discord users can trigger Luna), the configurable runner gathers repository and feature inputs across conversation turns, then runs the **full provisioning sequence**; **`launch_cursor_run`** is the authoritative launch path (not `cursor.fullRun`).

# Flow

1. A Discord message referencing `@Luna` matches the `luna` bot through routing (and satisfies `discordAuthors` when that filter is configured).
2. The configured runner executes `luna_cursor`: the first repo step uses `choiceProvider: githubRepos` to show "Use last repo", GitHub repos (from API, sort=updated), and "Custom repo"; if the user picks "Custom repo", a follow-up prompt captures free-text repo; then a prompt/capture for the code change; then a confirmation step (Launch / Edit repo / Edit request / Cancel) with summary (repo, branch, change). Discord can render choices as buttons or a select menu.
3. After the user confirms Launch, the flow runs the provisioning sequence: **create_channel** (bind **participantBotIds: [arrietty, architect, auditor, scribe]** for multi-bot permissions, or **lifecycleOwnerBotId** for single-owner; **DiscordSpaceOperations** calls gateway `createTextChannel` and applies permission overwrites for each; channel name derived from state when blank and normalized to Discord-safe; stores channel id or `CHANNEL_CREATE_FAILED`) → **branch** on `channelId == CHANNEL_CREATE_FAILED` → **provision_bot_instance** (Arrietty) → **create_lifecycle_context** → **create_thread** (storeIn: deliveryChannelId) → **provision_room_participants** (storeIn: featureRoomParticipants; reuses Arrietty runtime when valid) → **initialize_feature_room_state** → planning/repo steps → **get_profile_missing_fields** → **proposal-driven drafting (Arrietty intake thread):** **generate_planning_proposals** (`storeSpread`: **planningProposalsJson**, **planningConfirmQueueJson**, **planningHasConfirmPending**) → **apply_auto_planning_proposals** (writes **AUTO_APPLY** targets to **FeaturePlanState** artifacts; shrinks **planningProposalsJson**) → confirm loop while **planningHasConfirmPending**: **build_proposal_confirm_prompt** → **prompt_for_field** / **capture_field** (**discoveryAnswerRaw**) → **resolve_proposal_confirmation** (OK/yes/accept vs edited text) → **classify_assumption_or_issue** → **recompute_plan_progress** → branch → then **Phase B guided discovery** when gaps remain: **get_structured_discovery_gaps** (`storeSpread`), branch on **discoveryHasOpenGaps**, **build_discovery_agenda** (`storeSpread`), **prompt_for_field** / **capture_field** (**discoveryAnswerRaw**), **capture_and_apply_discovery_answer**, **classify_assumption_or_issue**, **recompute_plan_progress** (`storeSpread`), branch (loop with **clear** on **discoveryAnswerRaw** until no gaps or **discoveryBlockingIssueMode**) → **post_channel_message** (thread: orchestrator, architect, auditor, scribe role turns with **asRole** and **target: thread**) → **post_channel_message** (room summary as orchestrator) → **launch_cursor_run**. **Response policy:** Router returns four participant bot ids on the **intake thread**; the **room channel** routes to the coordinator only; Luna drives visible thread collaboration via explicit **post_channel_message** steps. `launch_cursor_run` uses `CursorInstructionComposer` to build the Cursor run prompt (single source; includes /nova-code), launches `POST /v0/agents`, stores `LifecycleRunRecord` and `luna:lastRepo:{authorId}`, and returns an acknowledgement that includes optional status (e.g. "Status: launching") and points to the lifecycle room.
4. `CursorCloudRunMonitor` polls `GET /v0/agents/{id}` and `GET /v0/agents/{id}/conversation` for state changes and assistant feedback.
5. The engine and monitor send launch/progress/final replies back to Discord when the source is Discord.

**Proposal pass:** Deterministic drafts for **overall_plan**, **validation_plan**, and **project_context** are classified as **AUTO_APPLY** when the repo workspace is ready (**MATERIALIZED** / **RESOLVED_LOCAL**); otherwise **CONFIRM** drafts (request-only) are shown with **OK** vs paste-edit before canonical upsert. **`synthesize_plan_drafts`** remains registered for legacy YAML but **arrietty_room** uses the proposal actions first.

**Phase B (structured discovery):** After the proposal pass, when **`get_structured_discovery_gaps`** reports open gaps, the **arrietty_room** thread path cycles **agenda → prompt/capture → apply required fields → classify answer**; gap prompts prefer **`userFacingDetail`** / profile copy over raw internal paths. **`classify_assumption_or_issue`** uses simple text rules to call **`append_plan_issue`** or **`append_plan_assumption`**; **`recompute_plan_progress`** re-spreads **`discoveryHasOpenGaps`** and **`discoveryBlockingIssueMode`**. The loop exits when there are no open gaps or **`discoveryBlockingIssueMode`** is true.

**Phase C (critique and approval):** **`run_plan_critique_and_readiness`** writes **`PlanCritiqueSnapshot`** and **`PlanConfidence`** on **`FeaturePlanState`** and spreads keys for Discord templates. Branches route **blocked** and **needs-revision** paths without calling **`launch_cursor_run`**; **approve** / **approve_with_risks** persist **`PlanApproval`** then continue to role handoff and launch.

**Lifecycle room (Phase 1):** The Luna workflow uses the full sequence above. **Multi-bot feature room:** Four participants—**Arrietty (Orchestrator)**, architect, auditor, scribe. **CreateRoomRequest** supports optional **participantBotIds**; Discord applies permission overwrites for each. **featureRoomParticipants** is a transient handoff from **provision_room_participants** to **initialize_feature_room_state** (typed **FeatureRoomState** in **FeatureRoomStateStore**). **Response policy:** room channel is coordinator-centric; intake thread receives all four routed bots for collaboration; **post_channel_message** uses explicit **asRole**/**asBotId** with strict sender resolution. Provisioning workflows (e.g. using the Arrietty template) follow the same create/provision/thread/initialize pattern, then explicit thread posts before `launch_cursor_run`. **Bootstrap** registers Discord SpaceOperations with the registry. `create_channel` and `create_thread` do **not** default to any connector; capability lookup is **fail-closed**. **SpaceOperations** uses **CreateRoomRequest**/**CreateThreadRequest**. The **done step** may use a short **main-room redirect** message (e.g. `"Launching now. See <#{{channelId}}>."`). Run state uses `LifecycleRunRecord` (optional `deliveryChannelId`); context uses `LifecycleContext` and `LifecycleContextStore`; multi-bot rooms use **FeatureRoomStateStore**. `CursorCloudRunMonitor` sends status and feedback to the thread when `deliveryChannelId` is set (messageId null).

# Inputs and outputs

- **Inputs:** Discord event content or mention metadata, configured Luna workflow steps, per-conversation gathering state, and Cursor API credentials from environment.
- **Outputs:** Updated gathering state, in-memory run-tracking state, Cursor-backed repository side effects (feature branch and PR), and workflow/monitor replies delivered to Discord.
