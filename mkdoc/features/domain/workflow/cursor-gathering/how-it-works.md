# How it works

# Overview

The shipped Luna flow is configured in `config/bots.yaml` as workflow `luna_cursor`. Routing activates the `luna` bot from `discordMention: luna` (and optional `discordAuthors` to restrict which Discord users can trigger Luna), the configurable runner gathers repository and feature inputs across conversation turns, then runs the **full provisioning sequence**; **`launch_cursor_run`** is the authoritative launch path (not `cursor.fullRun`).

# Flow

1. A Discord message referencing `@Luna` matches the `luna` bot through routing (and satisfies `discordAuthors` when that filter is configured).
2. The configured runner executes `luna_cursor`: the first repo step uses `choiceProvider: githubRepos` to show "Use last repo", GitHub repos (from API, sort=updated), and "Custom repo"; if the user picks "Custom repo", a follow-up prompt captures free-text repo; then a prompt/capture for the code change; then a confirmation step (Launch / Edit repo / Edit request / Cancel) with summary (repo, branch, change). Discord can render choices as buttons or a select menu.
3. After the user confirms Launch, the flow runs the provisioning sequence: **create_channel** (bind **participantBotIds: [arrietty, architect, auditor, scribe]** for multi-bot permissions, or **lifecycleOwnerBotId** for single-owner; **DiscordSpaceOperations** calls gateway `createTextChannel` and applies permission overwrites for each; channel name derived from state when blank and normalized to Discord-safe; stores channel id or `CHANNEL_CREATE_FAILED`) → **branch** on `channelId == CHANNEL_CREATE_FAILED` → **provision_bot_instance** (Arrietty) → **create_lifecycle_context** → **create_thread** (storeIn: deliveryChannelId) → **provision_room_participants** (storeIn: featureRoomParticipants) → **initialize_feature_room_state** → **post_channel_message** (e.g. asRole: orchestrator; content supports `{{key}}` interpolation, e.g. `lifecycleBotName: "Arrietty"`) → **post_channel_message** (thread; e.g. asRole: scribe) → **launch_cursor_run**. **Response policy:** In feature rooms the Router returns all four participant bot ids; only **Arrietty (Orchestrator)** replies by default; architect, auditor, scribe reply when invoked via action (asRole/asBotId). `launch_cursor_run` uses `CursorInstructionComposer` to build the Cursor run prompt (single source; includes /nova-code), launches `POST /v0/agents`, stores `LifecycleRunRecord` and `luna:lastRepo:{authorId}`, and returns an acknowledgement that includes optional status (e.g. "Status: launching") and points to the lifecycle room.
4. `CursorCloudRunMonitor` polls `GET /v0/agents/{id}` and `GET /v0/agents/{id}/conversation` for state changes and assistant feedback.
5. The engine and monitor send launch/progress/final replies back to Discord when the source is Discord.

**Lifecycle room (Phase 1):** The Luna workflow uses the full sequence above. **Multi-bot feature room:** Four participants—**Arrietty (Orchestrator)**, architect, auditor, scribe. **CreateRoomRequest** supports optional **participantBotIds**; Discord applies permission overwrites for each. **featureRoomParticipants** state key is set by **provision_room_participants** and consumed by **initialize_feature_room_state** (builds **FeatureRoomState** in **FeatureRoomStateStore**). **Response policy:** only Arrietty (Orchestrator) replies by default; others reply when invoked via **post_channel_message** with **asRole** or **asBotId**. Provisioning workflows (e.g. using the Arrietty template) run: `create_channel` (with participantBotIds or lifecycleOwnerBotId) → branch on `CHANNEL_CREATE_FAILED` → `provision_bot_instance` → **create_lifecycle_context** → **create_thread** (storeIn: deliveryChannelId) → **provision_room_participants** → **initialize_feature_room_state** → `post_channel_message` (optional asRole) → `launch_cursor_run`. **Bootstrap** registers Discord SpaceOperations with the registry. `create_channel` and `create_thread` do **not** default to any connector; capability lookup is **fail-closed**. **SpaceOperations** uses **CreateRoomRequest**/**CreateThreadRequest**. The **done step** may use a short **main-room redirect** message (e.g. `"Launching now. See <#{{channelId}}>."`). Run state uses `LifecycleRunRecord` (optional `deliveryChannelId`); context uses `LifecycleContext` and `LifecycleContextStore`; multi-bot rooms use **FeatureRoomStateStore**. `CursorCloudRunMonitor` sends status and feedback to the thread when `deliveryChannelId` is set (messageId null).

# Inputs and outputs

- **Inputs:** Discord event content or mention metadata, configured Luna workflow steps, per-conversation gathering state, and Cursor API credentials from environment.
- **Outputs:** Updated gathering state, in-memory run-tracking state, Cursor-backed repository side effects (feature branch and PR), and workflow/monitor replies delivered to Discord.
