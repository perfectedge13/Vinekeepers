# How it works

# Overview

The shipped Luna flow is configured in `config/bots.yaml` as workflow `luna_cursor`. Routing activates the `luna` bot from `discordMention: luna` (and optional `discordAuthors` to restrict which Discord users can trigger Luna), the configurable runner gathers repository and feature inputs across conversation turns, then runs the **full provisioning sequence**; **`launch_cursor_run`** is the authoritative launch path (not `cursor.fullRun`).

## Coordinator planning: operator-visible progress and copy

Coordinator and Arrietty intake threads are kept readable for humans while YAML branches stay machine-oriented:

- **Long-running phases:** Before expensive work (for example posting the full planning packet and running critique/readiness), coordinator progress copy names the next step so the thread is not silent. **`post_planning_packet_thread`** adds a short preamble before chunked packet bodies; optional **Update:** lines from **`OpenAiPlanningProgressPoster`** (wired as **`OpenAiPlanningProgressSink`** on **`OpenAiChatClient`**) fire before each contextualized planning HTTP call when **`OPENAI_PLANNING_DISCORD_PROGRESS`** is enabled.
- **Humanized status and labels:** **`PlanningUserFacingCopy`** and **`PlanningPromptFormatter`** (with **`config/work-profiles.yaml`** hints) supply plain-English readiness labels, checkpoint guides on **`REVIEWABLE`**, critique severities, profile field titles, and workspace summaries—avoiding raw enums, internal artifact paths, and pipeline jargon in Discord text.
- **Less duplicate review text:** **`BuildPlanningThreadReviewBodyAction`** prefers a short pointer when the packet is already visible in-thread; **`RunPlanCritiqueAndReadinessAction`** avoids repeating repo-grounding blocks after the packet; templates in **`config/bots.yaml`** trim redundant phrasing where the workflow already posted context.

# Flow

1. A Discord message referencing `@Luna` matches the `luna` bot through routing (and satisfies `discordAuthors` when that filter is configured).
2. The configured runner executes `luna_cursor`: the first repo step uses `choiceProvider: githubRepos` to show "Use last repo", GitHub repos (from API, sort=updated), and "Custom repo"; if the user picks "Custom repo", a follow-up prompt captures free-text repo; then a prompt/capture for the code change; then a confirmation step (Launch / Edit repo / Edit request / Cancel) with summary (repo, branch, change). Discord can render choices as buttons or a select menu.
3. After the user confirms Launch, the `luna_cursor` flow runs the provisioning sequence: **create_channel** (bind **participantBotIds: [arrietty]** for the Arrietty-owned planning room, or **lifecycleOwnerBotId** for single-owner fallback; **DiscordSpaceOperations** calls gateway `createTextChannel` and applies permission overwrites for each; channel name derived from state when blank and normalized to Discord-safe; stores channel id or `CHANNEL_CREATE_FAILED`) → **branch** on `channelId == CHANNEL_CREATE_FAILED` → **provision_bot_instance** (Arrietty) → **create_lifecycle_context** → **create_thread** (storeIn: deliveryChannelId) → **provision_room_participants** (storeIn: featureRoomParticipants; reuses Arrietty runtime when valid) → **initialize_feature_room_state** → **initialize_feature_plan_state** → **ensure_repo_workspace** → **upsert_artifact_section_data** → **post_channel_message** (intake/spec handoff in the thread) → **start_coordinator_planning**. From that kickoff onward, production **`arrietty_room_v2`** uses named v2 phases rather than a single linear runner: **`planning_ingress`** performs session hydration and workspace setup (**`hydrate_planning_session`**, **`ensure_repo_workspace`**, optional **`prep_planning_repo_grounding`**, **`spread_plan_workspace_signals`**, **`classify_planning_ingress`**), **`planning_kickoff`** runs **`coordinator_intake_bootstrap`**, **`planning_prepare`** handles **`get_profile_missing_fields`** plus the draft-first proposal/apply/accept path and optional **`spread_planning_workspace_blocker`** recovery loop, **`planning_autonomous_draft`** runs the autonomous expansion / inner-round cycle, and later graph branches cover clarification, packet posting, critique, human/preapproval review, approval hold/reset, blocked handling, and **`planning_launch`** before terminal **`done`** / **`failed`** outcomes. Production **`arrietty_room_v2`** does **not** run the old Phase B structured discovery loop before the first autonomous draft; those actions remain for legacy/test paths. **Response policy:** Router returns the **coordinator** configured bot id for **intake thread messages** and interactions (single planning ingress); the **room channel** routes to the coordinator only; Luna drives visible thread collaboration via explicit **post_channel_message** steps.
4. `CursorCloudRunMonitor` polls `GET /v0/agents/{id}` and `GET /v0/agents/{id}/conversation` for state changes and assistant feedback.
5. The engine and monitor send launch/progress/final replies back to Discord when the source is Discord.

**Coordinator auto-start:** After Luna seeds the intake thread handoff (`post_channel_message` with `target: thread`), `start_coordinator_planning` calls `VinekeepersEngine.dispatchCoordinatorPlanningKickoff` with a synthetic thread message (`channelId` and `threadId` = intake thread id). Only Arrietty runs (not via `EventBus`). The engine skips duplicate kickoffs when the thread session is already `WAITING_INPUT`, in progress (`stepIndex > 0`), or completed (conversational terminal). If the synthetic kickoff errors, or produces neither a reply nor a recorded kickoff side-effect post, the engine marks the coordinator session as failed and posts a fallback internal-error notice to the intake/spec thread instead of silently returning success. **Bootstrap** must register `start_coordinator_planning` on the shared `WorkflowActionRegistry` **after** constructing `VinekeepersEngine` so the action receives a non-null engine (otherwise kickoff is a no-op).

**Coordinator intake (YAML):** In `arrietty_room_v2`, synthetic **coordinatorKickoff** routes through **`planning_ingress`** to **`planning_kickoff`**, where **`coordinator_intake_bootstrap`** posts the kickoff update and advances canonical stage to **`DRAFTING`**. Key named v2 phases include **`planning_prepare`**, **`planning_autonomous_draft`**, **`planning_assess_clarification`**, **`planning_redraft_notice`**, **`planning_clarification`**, **`planning_packet`**, **`planning_critique`**, **`planning_human_review`**, **`planning_preapproval_review`**, **`planning_approval`**, **`planning_approval_hold`**, **`planning_revision_reset`**, **`planning_blocked`**, and **`planning_launch`** before terminal **`done`** / **`failed`** outcomes. There is **no** optional “add scope / must-haves / risks” solicitation step on the live path. `ArriettyV2WorkflowYamlTest` guards the production phase graph and bans `linear_workflow_ref` delegation in Arrietty config. After **`hydrate_planning_session`**, production YAML runs **`ensure_repo_workspace`**, optional **`prep_planning_repo_grounding`** when declared (Qdrant + Parquet-backed embedding cache for repo retrieval), then **`spread_plan_workspace_signals`** and **`classify_planning_ingress`** so **`planningRepoEvidenceJson`** can include **`planningRag*`** diagnostics when RAG ran and kickoff can branch into the right intake path.

**Proposal pass:** Deterministic drafts for **overall_plan**, **validation_plan**, and **project_context** are classified as **AUTO_APPLY** when the repo workspace is ready (**MATERIALIZED** / **RESOLVED_LOCAL**); otherwise **CONFIRM** proposals are still generated, but production **`planning_prepare`** auto-applies them via **`accept_pending_planning_confirmations`** (draft-first: no user OK round-trip before the first autonomous pass). Open questions are not treated as an editable proposal: the coordinator asks at most one concrete question at a time through post-draft clarification when policy selects **ask**, and the final packet uses **`None — ready to implement`** when nothing unresolved remains. **`synthesize_plan_drafts`** remains registered as a legacy helper, but production Arrietty runs the proposal actions inside `arrietty_room_v2`.

**Structured discovery (legacy / tooling):** Workflow actions **`get_structured_discovery_gaps`**, **`build_insight_discovery_agenda`**, and **`capture_and_apply_discovery_answer`** remain registered for tests and non-v2 paths. Production **`arrietty_room_v2`** no longer runs the Phase B discovery loop inside **`planning_prepare`** so the first autonomous draft is not blocked on profile-field gaps or early coordinator prompts; **`spread_planning_workspace_blocker`** may still pause for a **single** workspace failure recovery prompt when the plan workspace is **`FAILED`**/**`UNAVAILABLE`**. **`ClarificationPromptQualityGate`** still applies where discovery agendas are built. **Open questions** in the posted packet are derived from **unresolved** plan rows/state, not ad hoc LLM lists (**PlanningArtifactTexts.substantiveUnresolvedQuestionLines** drops generic meta filler before tables); internal pipeline/JSON failures stay off user-visible thread copy (logs and debug spreads only).

**Post-draft canonical clarification (`canonical_v1`):** After expansion + inner rounds, **`planning_assess_clarification`** runs **`planning_finalize_cycle_spread`** (partial pipeline **`finalizePlanningCycleSpread`**). **`PlanningPostDraftGovernor`** sets **`planningPostDraftAction`** (`ASK_ONE_QUESTION`, `ASSUME_AND_CONTINUE`, `POST_PACKET`, `BLOCK`, or `AUTONOMOUS_REDRAFT`) from assessed gaps, depth/parse health, ledger repeat, and material-change / revision-situation fingerprints; when a path would otherwise **assume through** but **material structured gaps** remain (unresolved questions, open blocking issues, open HIGH assumptions, etc.), **`ASK_ONE_QUESTION`** forces **one concrete clarifying question** for that cycle. v2 **`rs_post_draft`** rules branch **only** on that action (default phase **`planning_blocked`** if unset). Legacy truthy **`planningUserInputRequired`** / **`planningReadyToPostPacket`** pairs are no longer the routing source. **`planning_redraft_notice`** posts **`planningPostDraftNoticeMarkdown`** and returns to **`planning_autonomous_draft`** only when the action is **`AUTONOMOUS_REDRAFT`**. **`ClarificationEngineAssessor`** (with **`CoordinatorClarificationGapEvaluator`** and work-profile **`coordinatorClarification.engine`**, including **`clarificationAskPriorityThreshold`**) ranks gap candidates using merged plan text and **`planningRepoEvidenceJson`**. Outcomes are **ask user**, **assume and continue**, **low-priority defer**, or **block as unimplementable**; profile-backed blocking gaps can now force a concrete model-routing clarification such as **per named step** vs **step type/phase** overrides, while non-blocking **asks** are deferred until **`FeaturePlanState.autonomousPlanningPassCompleted`** is true (the split v2 draft path now mirrors **`execute`** by persisting that flag when finalize completes without cycle error). **`FeaturePlanState`** records **`clarificationTurnsCompleted`**, **`clarificationOutcomeHistory`**, and **`clarificationCoordinatorLedgerJson`** (assessed gaps / next ask snapshot) for budget and audit. **`PlanningPacketDepthEvaluator`** can relax supplemental open-question heuristics when **`planningCanonicalUserInputRequired`** is false so generic filler does not hard-block packet posting while clarification is already clear.

**Planning RAG (optional):** When ingress declares **`prep_planning_repo_grounding`**, the coordinator path may index the materialized checkout into Qdrant and surface **`planningRagRetrievalText`** in **`run_llm_planning_synthesis`** when **`planningRagAvailable`**; otherwise planning continues without retrieval. Env and contracts: **env** feature dossier and **workflow-steps** contracts.

**Planning governance spine (coordinator):** **`derive_plan_governance`** (and **`PlanningCyclePipeline`** before “ready to post”) merges discovery gaps and artifact text into canonical **`PlanIssue`** / **`PlanRisk`** / **`PlanDecision`** rows on **`FeaturePlanState`** so the packet and critique share one source of truth. **`PlanGovernanceDeriver`** de-duplicates open-question lines from the artifact backlog with existing unresolved-question rows so displayed **open questions** reflect **unresolved** state, and normalizes repeatable **decision log** text into distinct rows for labeled packet display, without changing Phase B's **at most one** blocking user question per cycle. Live-cycle **`PlanningQuestionRankingPolicy`** enforces the same **one concrete blocking ask** discipline where legacy ranking applies; **`canonical_v1`** adds **`ClarificationEngineAssessor`** so post-draft coordinator turns can **assume** or **defer** instead of always prompting. When the draft is ready to move forward, the coordinator progress copy says the next long step is posting the planning packet and running readiness checks. **`evaluate_planning_packet_depth`** still gates **`post_planning_packet_thread`**; **`PlanningThreadPacketFormatter`** reads those lists and renders **Discord-facing labeled list items** for **assumptions**, **issues**, **risks**, **decisions**, and **open questions**, with humanized inline fields via **`PlanningUserFacingCopy`**. Multi-line **user stories** and **acceptance criteria** can gain an extra numbered **list** when at least two bullet or numbered lines are present. Long narrative sections are **soft-truncated** with an explicit italic footnote *(Truncated for display length.)*; capped inline item text ends with an ellipsis. **`BuildPlanningThreadReviewBodyAction`** adds an explicit "truncated to fit the workflow cap" footnote when pre-approval review bodies hit size limits (no silent cut). Empty sections use **`_Not drafted yet._`** or **`_None recorded._`**. **`execute_planning_room_cycle`** may run **`run_request_expansion_llm`** first so structured JSON (candidate open questions, profile **`upserts`**, and related fields) merges into artifacts before deterministic exploration, complementing coordinator-led clarification. When **`OPENAI_API_KEY`** is set, **`OpenAiChatClient`** (wired with **`OpenAiPlanningProgressPoster`** as **`OpenAiPlanningProgressSink`**) posts short **Update:** progress lines to the workflow channel before each contextualized planning HTTP call unless **`OPENAI_PLANNING_DISCORD_PROGRESS`** is false; **`OpenAiCallContext.activitySummary`** drives the text. Server logs include per-call duration and, unless **`OPENAI_LOG_PLANNING_BODIES`** is false, truncated `sk-*`-redacted system/user/assistant payloads (capped by **`OPENAI_LOG_BODY_MAX_CHARS`**). On success, **`post_planning_packet_thread`** emits a brief preamble before packet chunks (each chunk labeled **Planning packet** or **part N/M** when split), then records **`packetPostedAt`**, fingerprint, and chunk count on the plan. **`run_plan_critique_and_readiness`** runs deterministic critique, **`PlanCritiqueRubric`** rollups, and **`PlanReadinessCalculator`**, persists **`PlanCritiqueSnapshot`** plus **`PlanConfidence`** (**readiness**, **confidenceScore**, **confidenceReasons**, **structuredKnownFactCount** / **materialUnknownCount** / **materialUnknownLabels** for known-vs-unknown facts), spreads **`planningCritiqueNextAction`** plus one compact next-action summary, and keeps **reviewability** separate from **approval eligibility**. **`REVIEWABLE`** means the packet is coherent enough for a human checkpoint, but approval still stays closed until confidence and approval gates are satisfied. **`evaluate_planning_approval_gate`** loads the plan from **`FeaturePlanStateStore`** and requires posted-packet metadata, completed critique, **READY** or acknowledged **CONDITIONALLY_READY** readiness, **confidenceScore** ≥ **`PlanReadinessCalculator.APPROVAL_CONFIDENCE_THRESHOLD`** (**0.85**) when a score is persisted, and canonical intake/clarification posture—workflow flags alone are not enough. The review prompt no longer promises buttons unless the interactive path is actually available; the text fallback is to reply with `continue` or `revise`. **`persist_plan_approval`** is fail-closed for approve paths when those checks fail.

**Phase C (critique and approval):** **`run_plan_critique_and_readiness`** writes enriched **`PlanCritiqueSnapshot`** and **`PlanConfidence`** on **`FeaturePlanState`**, spreads readiness/critique keys, and merges **`planningThreadReviewBody`** / **`planningThreadReviewBuildError`** (same content as standalone **`build_planning_thread_review_body`**) so the orchestrator **`post_channel_message`** can show drafted outline/validation/context before approval buttons. **`PlanningUserFacingCopy`** supplies Discord-facing wording (**`planReadinessStatusLabel`**, **`planReadinessCheckpointGuide`** when status is **`REVIEWABLE`**, humanized critique severities in the review body) while YAML phases keep using machine **`planReadinessStatus`** values. The checkpoint guide is explanatory only, and the interactive prompt now includes a truthful plain-text fallback (`continue` / `revise`) instead of always promising buttons. Canonical **`PlanningIntakeStage`** is the source of truth for whether discovery has advanced beyond context gathering, so critique and approval gates no longer depend on a parallel workflow-only completion flag. Phases route **blocked**, **clarification**, **internal revision**, **review checkpoint**, and **approval** paths without silently auto-replanning after a visible human checkpoint; **approve** / **approve_with_risks** persist **`PlanApproval`** and **`launch_cursor_run`** spreads **`launchSucceeded`** / **`launchMessage`** for success vs failure thread messaging. Optional **`CURSOR_HTTP_*_TIMEOUT_MS`** tune Cursor API client timeouts. **VinekeepersEngine** sends a minimal follow-up for **deferred** Discord interactions when the workflow produces no outbound reply, and it no longer degrades rich interaction intents into plain-text legacy replies when no sink is available.

**Lifecycle room (Phase 1):** The Luna workflow uses the full sequence above. **Arrietty-owned feature room:** Arrietty is the sole planning participant and coordinator. **CreateRoomRequest** supports optional **participantBotIds**; Discord applies permission overwrites for each. **featureRoomParticipants** is a transient handoff from **provision_room_participants** to **initialize_feature_room_state** (typed **FeatureRoomState** in **FeatureRoomStateStore**). **Response policy:** room channel is coordinator-centric; intake **thread messages** route to the **coordinator** only (same as interactions); **post_channel_message** uses explicit **asRole**/**asBotId** with strict sender resolution. Provisioning workflows (e.g. using the Arrietty template) follow the same create/provision/thread/initialize pattern, then explicit thread posts before `launch_cursor_run`. **Bootstrap** registers Discord SpaceOperations with the registry. `create_channel` and `create_thread` do **not** default to any connector; capability lookup is **fail-closed**. **SpaceOperations** uses **CreateRoomRequest**/**CreateThreadRequest**. The shipped Luna **done** step points operators back to the intake/spec thread using **`deliveryChannelId`**. Run state uses `LifecycleRunRecord` (optional `deliveryChannelId`); context uses `LifecycleContext` and `LifecycleContextStore`; feature rooms use **FeatureRoomStateStore**. `CursorCloudRunMonitor` sends status and feedback to the thread when `deliveryChannelId` is set (messageId null).

# Inputs and outputs

- **Inputs:** Discord event content or mention metadata, configured Luna workflow steps, per-conversation gathering state, and Cursor API credentials from environment.
- **Outputs:** Updated gathering state, in-memory run-tracking state, Cursor-backed repository side effects (feature branch and PR), and workflow/monitor replies delivered to Discord.
